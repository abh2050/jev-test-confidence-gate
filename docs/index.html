The last row is why this repo is named after the gate rather than the model. It is the claim that would change how you build — and the one a 24-ticket workload turns out to be worst at testing.

01 · The setup

Hold the graph fixed, swap the judgment

The premise is that a decision layer is a component, not a personality. Every question — its wording, its rubric, its options — is defined once, engine-neutral. Jev compiles those specs into System One primitives; the OpenAI engine compiles the identical specs into a strict JSON schema plus the same rendered rubrics. Nothing about the prompt differs between runs.

Everything downstream is ordinary code: thresholds, SLA clocks, refund limits, the legal override. Both engines are judged against the same rules, so the only variable is where the probabilities came from.

An engine implements one method — ask(state, questions) — and returns typed values with probabilities. It never decides what the application does.

02 · The system under test

A supervisor and three subgraphs

One triage call asks five independent judgments in parallel over the same ticket. A gate node then turns those probabilities into a branch — in plain code, with no model involved — and the ticket enters one of three compiled subgraphs, each attached to the parent as a single node.

The gate is the whole experiment in one node. An uncertain department choice is not resolved by guessing — it routes to a human. That only works if the confidence number means something.

Where the model stops and code starts

Judgment — model
Decision — code
department + probabilities
which subgraph runs, and whether confidence is high enough to trust it at all
priority, 0–3 expected score
the SLA clock: 72h / 24h / 8h / 1h
action + policy_exception
the refund amount, and whether a supervisor must approve it
severity, data_loss_risk
whether to page on-call
tier, legal_exposure
the legal override, which no weighted score can average away

Two consequences. Changing the refund limit doesn't re-run inference — the judgments are unchanged, only the policy reading them. And the model is never asked what to do, only to describe the situation.

03 · The claim that holds

Time to decision

7.1× faster to a routing decision
163 ms vs 1164 ms, mean of 24 tickets

Both engines make exactly two requests per ticket and ask exactly the same questions. The difference is what comes back: typed judgments return a short structured answer, where prompt-and-parse has to emit a JSON object token by token. Five parallel questions cost one response either way — the responses just aren't the same size.

Graph overhead was 3.7 ms and 3.6 ms respectively — which is the number that makes the rest of this page worth reading. The harness is not what's being measured.

One caveat on the multiple

TypeSafe claims 40–200×. This run shows 7.1×, and that is not a contradiction — it's a comparator choice. gpt-4o-mini is a small, non-reasoning model, about the fastest thing you could put on the other side of this comparison. Their multiples are measured against frontier reasoning models. The absolute number is the one to trust here: 163 ms, inside their claimed 70–500 ms band.

04 · The claim that holds for a surprising reason

Cost, and where the saving actually comes from

6.1× cheaper per ticket at list price
$0.06 vs $0.37 per 1,000 tickets

The obvious story would be that parallel sampling means Jev emits far fewer output tokens. It doesn't. The output token counts were nearly identical — 4,573 against 4,487 across the same 48 requests.

The saving is on the price sheet, not the volume: output billed at zero, and input at $0.042/MTok against $0.15. If you were expecting the architecture to show up as a smaller response, it doesn't. It shows up on the invoice.

07 · The claim that did not land

Calibration: not demonstrated

This is the claim the whole experiment was built around, and the one it failed to confirm. Put three rows side by side:

department accuracy0.875 → 3 tickets wrong
abstention rate0.083 → 2 tickets gated
errors caught by gate0.000 → no overlap

Jev got three tickets wrong. It abstained on two. They were different tickets. It gated answers it had actually gotten right, and its real errors went through with high confidence. A confidence separation of −0.010 says it plainly: on this set, the number was very slightly anti-correlated with being right.

Two qualifications, in both directions

This does not refute the claim. Three errors is not a sample. A calibration measurement driven by three data points has essentially no statistical power, and both ECE and confidence separation need hundreds of cases to stabilise. The correct reading is "this workload could not test it," not "the claim is false."

It also isn't nothing. The gate is precisely the thing you would build on a calibration guarantee, and on this workload it did not work. That's worth knowing before you design around it.

Also don't credit this

The calibration column nominally favours gpt-4o-mini (0.150 vs 0.199). Ignore it. A predictor that always answers 0.9 scores well on calibration error whenever 0.9 happens to sit near its overall accuracy — which is roughly what happened. Confidence separation is the column that catches that, and at −0.000 it says the number carried no information about correctness at all. Neither engine earned this row.

So the honest claim is narrow. Jev's confidence varies — 0.32, 0.42, 0.55 on genuinely ambiguous tickets — where the other engine reported 0.9 on nearly everything. A varying signal is a precondition for the gate to do anything; a pinned one makes it dead code at any threshold. But varying is not the same as useful, and this run does not show the gate working.

08 · What would settle it

What would settle the open question

The calibration claim needs a workload where the error count is large enough to measure against — a few hundred real tickets, not 24 invented ones. Every accuracy metric here moves in steps of four percentage points; the confidence metrics are worse, driven by however many tickets the engine got wrong.

Running the suite twice makes the instability visible: Jev picked the same department on all 24 tickets both times, but needs_human accuracy moved 0.667 → 0.583 and the abstention rate 0.125 → 0.083, purely from probabilities drifting across a fixed threshold. Until the sample is bigger, the speed and cost claims are the ones this repo can vouch for.

Caveats

The 24 tickets are invented and the labels are one reviewer's judgment, about a third of them deliberately ambiguous. The policy thresholds are starting points, not validated defaults. Prices are hand-entered list prices and go stale. A third engine, Gemini, ran correctly but exhausted its free-tier quota after 7 tickets and was removed rather than reported on a different denominator.
